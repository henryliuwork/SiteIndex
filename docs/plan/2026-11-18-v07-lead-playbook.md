# SiteIndex · v0.7.x 目标模式 · Lead Agent 运行手册（2026-11-18）

> 适用：`v0.7.0`、`v0.7.5`。范围与验收见 `docs/plan/2026-11-18-v070-v075-roadmap.md`。
> lead 与五个工作流 agent（A/B/C/D/E）都必须读本手册。

## 1. 角色与权限

### Lead 负责
持续监控进度、分派与解阻塞、对照 Gate 核对证据、**合并 PR**、**发布版本**、分类并裁决缺陷、维护看板、向用户汇报。

### Lead 不得
1. 修改范围、验收标准或 Gate（只有用户可以）。
2. 新增功能、把 backlog 缺陷提升进当前版本、修改本手册 §5 的准入条件。
3. 在 CI 未全绿（Windows、macOS、Ubuntu）时合并；用 `--admin` 或强推绕过检查。
4. 自己写业务代码（可以写 `docs/` 与看板；代码一律由对应工作流完成）。
5. 在"契约语义变更"（不只是加字段）时自行决定：必须通知用户。
6. 允许任何真实站点信息进入仓库。

### 必须通知用户（且停止相关合并）的事件
- Gate 验收失败且 2 轮修复未解决。
- 需要改范围、阈值、时间盒，或有人提出新增功能。
- 契约语义变更；`main` 的 CI 连续两次非偶发失败。
- 发现"阻断安装与启动"或"数据丢失"类缺陷。
- 公开仓库红线疑似被触及（真实域名、凭据等）——先清除再通知。

其余事项 lead 自行裁决，事后在看板记录。

### 工作流 agent
只改自己的目录（`docs/WORKSTREAMS.md` §1），不合并任何 PR（包括自己的），不自行裁决缺陷归类，向 lead 汇报。

## 2. 目标定义

> **目标**：按 roadmap 的 Gate 顺序，发布 `v0.7.0`，随后发布 `v0.7.5`；每个版本都满足全部退出标准，且不扩大范围。
> **完成** = 所有 Gate 记录"通过" + Release 已发布 + E 的验收报告已入看板 + 用户收到"改进 / 建议测试"清单。
> **未完成但必须停止** = 触发 §1 的通知事件，或时间盒超过规定天数。

## 3. 看板与汇报

### 3.1 看板
Lead 创建两个置顶 issue：`[lead] v0.7.0 进度看板`、`[lead] v0.7.5 进度看板`，正文是一张表，由 lead **独占编辑**：

| Gate | 状态（未开始/进行中/阻塞/通过） | 负责 | 证据链接 | 最近更新 |
|---|---|---|---|---|

并包含三个区块：**开放 PR 队列**、**阻塞项**、**范围内缺陷**（含"已修轮次"）。backlog 缺陷只标 label `backlog`，不进看板。

### 3.2 工作流汇报
各 agent 只在对应看板 issue 下**评论**，不得编辑正文。汇报时点：
1. **开工**：确认已读 roadmap 与手册，列出本轮要做的任务编号。
2. **PR 提交**：PR 链接、对应任务编号、CI 状态、`ui:check`（涉及 UI）、截图（涉及 UI）。
3. **阻塞**：阻塞原因、已尝试什么、需要谁做什么。**阻塞超过 1 个监控周期必须汇报**，不得默默等待。
4. **Gate 完成**：对照退出标准逐条打勾 + 证据。
5. **发现缺陷**：不得自行修复，先按 §5 开 issue 并提交归类建议。

汇报模板（评论正文）：
```
[工作流] A|B|C|D|E   [阶段] G7.x-n
任务：<编号>
状态：进行中 | 已提交 PR | 阻塞 | 完成
证据：<链接>
退出标准：[x] ... [ ] ...
风险/需要 lead：<一句话，没有则写"无">
```

### 3.3 监控周期
- 默认每 **30 分钟**或收到任一 agent 汇报时执行一次 §4 的循环；agent 有任务进行中时不得连续空转超过 **2 小时**不汇报。
- 夜间或无人值守：每 60 分钟一次；只做 §4 的检查、合并与记录，不做裁决类事项，裁决类事项累积到用户在线时一并报告。

## 4. 监控循环（每个周期按顺序执行）

1. 读 main 最新提交与 CI 状态；main 红则**冻结合并**，先定位（§6.3）。
2. 列出 open PR：CI、冲突、`mergeable_state`、是否对应已认领的任务编号。
3. 对每个**符合合并门槛**（§4.1）的 PR 立即合并；`dirty` 的 PR 要求作者 rebase。
4. 读新增评论与 issue：按 §5 分类、分派。
5. 检查每个 Gate 的退出标准，满足则记录"通过"并通知下一阶段 agent 开工。
6. 核对时间盒：到期前一天列出风险；到期按 roadmap §7 处理。
7. 更新看板；若有 §1 的通知事件，立即汇报用户。

### 4.1 合并门槛（全部满足才可合并）
- 三系统 CI 全绿（本地通过不算）。
- PR 对应 roadmap 的任务编号，且在作者工作流的目录范围内（用文件列表核对）。
- PR ≤ 600 行改动；超出须 PR 描述说明，且 lead 确认无法拆分。
- 涉及 UI：附 `pnpm ui:check` 输出，**无新增样式违规**；附 1280×800 与 1920×1080 截图。
- 涉及依赖：同时提交 `pnpm-lock.yaml`，PR 说明新增依赖原因与体积。
- 改 `packages/shared/` 的只能是 `contract/*` 分支，且同一时间只有一个未合并的 contract PR。
- 不含真实站点、凭据、真实客户数据。
- 标题前缀 `[A]`/`[B]`/`[C]`/`[D]`/`[contract]`/`[docs]`/`[fix]`（缺陷修复，见 §5）。
- 合并方式：以 PR head sha 固定的普通 merge，不 squash 他人提交。

### 4.2 PR 的基线规则
每个 PR 基于最新 `main`，不叠在未合并分支上；先合并的优先，后合并的负责 rebase。

## 5. 问题处理流程与 Bugfix Workflow（严禁无限制扩大修复）

### 5.1 范围内缺陷：只有三类
| 类 | 定义 | 判定问法 |
|---|---|---|
| **R 回归** | 本版本引入的问题：在上一个已发布版本上不存在，在候选版本上出现 | 用上一版安装包或 tag 复现，能复现则**不是** R |
| **D 数据** | 数据错误或丢失：计数不对、写入错误、文件被覆盖或丢失 | 是否使数据文件或读回数字与事实不符 |
| **B 阻断** | 阻断安装、启动、升级，或使该版本目标功能完全不可用 | 用户是否无法完成该版本的 Gate 所描述的主流程 |

**其余一律进 backlog**，包括但不限于：样式瑕疵、文案、性能优化、历史问题、"顺手可以更好"的重构、边缘平台差异、E 发现的非三类问题。backlog 缺陷：打 label `backlog`，写入 issue，**不得在本版本排期**；是否在下个版本做由用户决定。

### 5.2 分类流程
1. **发现者**（任何 agent）开 issue，使用模板：现象 / 复现步骤 / 复现版本（候选版本与上一发布版本各试一次）/ 影响面 / **归类建议（R、D、B 或 backlog）与理由**。
2. **lead 在一个监控周期内**裁决：写评论"归类：R|D|B|backlog，理由：…"；非 R/D/B 的立即打 `backlog` 并结案（关闭为 not planned）。
3. 归类争议：以**可复现的证据**为准；无法复现的不算；lead 仍不确定时**默认进 backlog**。
4. R/D/B 才分派给对应目录的工作流，并打 label `v07-fix`，在看板"范围内缺陷"区登记，轮次记 0。

### 5.3 修复上限（防扩张）
- 每个缺陷**最多 2 轮修复**：第 1 轮修复后 E（或作者）复验；未解决则第 2 轮；第 2 轮仍未解决 → **停止**，lead 通知用户裁决（回滚、延期、降级为已知问题）。
- 每个修复 PR **≤ 200 行**改动（含测试）；超出视为扩大范围，须拆分或升级为用户决策。
- 每个版本的修复 PR 总数**不得超过该版本功能 PR 数的 30%**；达到上限后，lead 不再接收新的 `v07-fix`，剩余的 R/D/B 以外一律 backlog，R/D/B 则通知用户。
- 一个 PR 只修一个缺陷。

### 5.4 Bugfix Workflow（执行修复的 agent 必须逐步遵守）
1. **确认 issue 已被 lead 归类为 R/D/B 并打 `v07-fix`**；否则不得动手。
2. **先写失败测试**（或可重复的 `ui:check` 断言 / 夹具），在 PR 描述里贴出修复前失败的输出。无法自动化的 UI 缺陷，用修复前后截图代替，并说明原因。
3. **找根因**，在 issue 里写一句根因；只修根因，不修症状的旁支。
4. **最小修改**：只改与根因直接相关的文件；**不顺手重构、不改风格、不重命名、不升级依赖、不加功能**。
5. 修复 PR 标题 `[fix] <一句话> (fixes #N)`，基于最新 main，改动 ≤ 200 行。
6. PR 描述必须包含：根因、修改文件清单、修复前后证据、"未改动的邻近问题"（如有，列成新 issue 链接并已归类）。
7. 三系统 CI 全绿 → lead 合并。
8. **复验**：E（或对应 Gate 负责人）只复验该缺陷本身及其直接依赖路径，不得借机扩大走查；结果写在 issue 评论。
9. lead 关闭 issue，并更新看板的"已修轮次"。
10. 若复验失败：轮次 +1；到 2 轮仍失败按 §5.3 升级。

### 5.5 禁止事项
- 在修复 PR 里夹带无关改动或"清理"。
- 修复过程中发现邻近问题就地一起修（必须开新 issue 并先归类）。
- 以"为了验收通过"为由把 backlog 缺陷改归类为 R/D/B。
- 修复 backlog（含老 issue #3 ~ #507 区间的历史问题）——本轮一律不碰，除非 lead 记录它被本版本的变更重新引入（此时它即为 R，需附复现证据）。
- 调整 Gate、阈值、时间盒来"让验收通过"。

## 6. 异常处理

### 6.1 阻塞
agent 阻塞超过 1 个周期 → lead 判断：能由另一个工作流解决则分派；需要契约则排入 contract 队列；需要用户则通知。**不得**让 agent 绕开目录边界自己动手。

### 6.2 冲突与并行
- 文件冲突：后提交者 rebase；同一文件被两个 PR 修改时，由先开工者先合并，lead 在看板标注顺序。
- contract 队列：任意时刻只允许 1 个 `contract/*` PR 处于开放状态；A 负责 `shared` 的写入，其他人提需求给 A。

### 6.3 CI 失败
- 同一测试第一次失败：可重跑 1 次；通过则记录为 flaky，开 issue 打 `flaky` + `backlog`，**不阻塞**。
- 重跑仍失败：视为真实失败，必须修复后才能合并；若失败来自历史代码而与 PR 无关，lead 判断是否属于 R/D/B，否则暂停合并该 PR 并通知用户。
- `main` 红：冻结合并；定位是哪个合并引入（R 类，直接修复，不占 30% 上限）。

### 6.4 工作流 agent 失联或无输出
超过 2 个监控周期无汇报：lead 在看板评论询问；再 1 个周期无响应则标记阻塞并通知用户，由用户重新分派。

## 7. 发布流程（lead 执行；用户已授权发版）

发布前逐项核对（全部满足才发）：
1. 该版本所有 Gate 记录"通过"，证据链接都能打开。
2. `main` CI 三系统全绿，且发布提交即该 CI 所验证的提交。
3. 版本号 PR（C）已合并：桌面端、CLI、MCP 的版本字符串一致。
4. Windows 安装包校验：自定义目录连续安装两次的完整性检查、`--run-job` 校验、`resources/fonts` 存在、字体离线加载。
5. E 的验收报告已入看板，范围内缺陷（R/D/B）为 0 个未关闭。
6. Release notes 包含两个固定小节：**本版本改进**（面向用户的变化）、**建议测试**（用户该点哪些页面、检查什么）。
7. 打 tag，发布；把 Release 链接和上述两个小节发给用户。

## 8. 数据红线
所有 PR、issue、评论、截图、fixture：只使用虚构域名（`example.test`）与合成数据。发现真实站点信息：立即编辑或删除原评论（如需，用户协助），在 PR 中修正，再通知用户；**不得**以"已打码"替代清除。

## 附录 A · Lead 启动指令（用户一次性发给 lead）

```
你是 SiteIndex v0.7.x 的 lead agent，目标模式。
先 git pull 最新 main，读：
1. AGENTS.md
2. docs/plan/2026-11-18-v070-v075-roadmap.md
3. docs/plan/2026-11-18-v07-lead-playbook.md
然后执行：
1. 创建两个置顶看板 issue（v0.7.0、v0.7.5），按手册 §3.1 的格式。
2. 在 v0.7.0 看板下，给 A/B/C/D/E 各发一条开工指令，内容使用附录 B，并附上该工作流在 roadmap §4 与 §5 里的任务编号。
3. 按手册 §4 的监控循环持续工作，直到 §2 的"完成"或"必须停止"条件成立。
你不得改范围、验收标准与 Gate；不得扩大 bug 修复（§5）。遇到 §1 的通知事件，立即向用户汇报并停止相关合并。
```

## 附录 B · 工作流 agent 启动指令（由 lead 在看板中发布，或用户逐个发给 A/B/C/D/E）

```
你是 SiteIndex 的工作流 <A|B|C|D|E>。你向 lead agent 汇报，不向用户汇报。
先 git pull 最新 main，读：
1. AGENTS.md 与 docs/WORKSTREAMS.md §1（确认你的目录边界）
2. docs/plan/2026-11-18-v070-v075-roadmap.md（本轮范围与验收；你的任务在 §4，Gate 在 §5）
3. docs/plan/2026-11-18-v07-lead-playbook.md（汇报、PR 门槛、缺陷流程）

规则：
- 只改自己目录；不合并任何 PR；每个 PR 基于最新 main，≤ 600 行。
- 只做 roadmap 里列出的任务编号；不加功能，不顺手重构。
- 发现缺陷：不修复，按手册 §5.2 开 issue 并给归类建议，等 lead 归类。
- 被归类为 R/D/B 的缺陷，严格按手册 §5.4 修，PR ≤ 200 行，最多 2 轮。
- 阻塞超过一个周期必须汇报。汇报使用手册 §3.2 的模板，评论在对应看板 issue 下。
- 仓库公开：只用虚构域名与合成数据。
```
