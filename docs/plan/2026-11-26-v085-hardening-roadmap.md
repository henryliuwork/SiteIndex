## 2. 目标与非目标

**目标**
1. 共享组件尺寸与规范一致，`ui:check` 例外只减不增，并覆盖 Windows 125%、150% 缩放的有效视口。
2. 表格规范成为正式条款并有自动断言。
3. 一套统一的 Windows 安装版验收脚本规范与共享库，取代各脚本重复的启动、退出、清理逻辑。
4. 产品错误带可诊断信息（错误码、操作、脱敏命令与 stderr），并据此处理 #807。
5. 小版本准入规则落地，补齐 v0.8.3、v0.8.4 的记录，清理遗留分支和 PR。

**非目标**：新功能；字体改动；数据抓取逻辑；设置页拆分；其他页面结构重构；放宽任何 `ui:check` 阈值；契约语义变更（除 §3.3 的可选字段）。

### 3.3 错误可诊断（A 牵头，C 配合；含一个 contract PR）

**契约 `contract/v085-error-detail`（唯一一个 shared 变更，仅新增可选字段）**：

```ts
interface ErrorDetail {
  code: string;            // 错误码，登记在 docs/ARCHITECTURE.md 的错误码表
  operation: string;       // 如 settings.set / schedule.verify
  command?: string[];      // 脱敏后的 argv
  exitCode?: number;
  stderr?: string;         // 脱敏后，≤2048 字符
  cause?: string;
}
```

规则：
1. `settings.*`、`projects.updateConfig`、`schedule.*`、`readme.*` 的失败必须带 `ErrorDetail`；堆栈只写应用日志，不经 IPC 返回界面。
2. 脱敏：用户目录替换为 `~`；凭据、token、Cookie 模式一律打掩码；绝不输出凭据值、文件内容。
3. 测试：用**金丝雀字符串**（合成的假凭据）走一遍所有上述错误路径，断言返回值与日志中均不出现金丝雀。
4. 界面不新增任何展示控件；用户可见信息仍是原有 toast 文案。详细信息供日志与验收脚本读取。

**#807 的处理（C）**：
1. 在 `schedule.verify` 捕获并返回 `ErrorDetail`（命令、退出码、脱敏 stderr）。
2. 用一次 Windows 托管合成运行读取真实原因，写入 #807。
3. 若定位成功：至多一次定向修复 PR（≤200 行、最多 2 轮），修复后 #52–56 在验收中恢复原标准 `verify=ok`，D18/D19 例外失效；若仍无法定位：保持 backlog，例外不变。

### 3.4 验收脚本规范（C 牵头写共享库，E 写 `docs/ACCEPTANCE.md` 并验收）

规则 H1–H10（写入 `docs/ACCEPTANCE.md`，同时在 `AGENTS.md` 保留摘要）：

| # | 规则 |
|---|---|
| H1 | 正常退出（WM_CLOSE / 应用正常退出），不强杀进程；强杀只允许出现在明确标注为"崩溃恢复"的专项用例 |
| H2 | 每个设置项使用独立会话与独立 profile，不连续复用 UI 会话 |
| H3 | 等待可观察状态（轮询 + 超时），禁止固定 sleep |
| H4 | 定位使用 role 或 `data-testid`，不使用页面文本；设置页关键控件补 `data-testid`（C 与 B 协调，只加属性） |
| H5 | 失败必有产物：错误消息与堆栈、截图、控制台、最近一次 IPC 调用（脱敏）。禁止只报 "Error" |
| H6 | 只用合成数据（`.example.test`）与隔离 profile/APPDATA；结束必清理，清理遇 EBUSY 要重试，清理失败单独记录，不得掩盖断言结果 |
| H7 | 统一报告 schema：条目 id、阶段、状态、证据 |
| H8 | 状态区分 `assertion_failed`（断言不成立）与 `harness_error`（脚本自身出错，如定位失败、清理失败）；lead 归类时先看这个字段 |
| H9 | 基线包与候选包均 SHA 校验 |
| H10 | 单一入口：一个可复用工作流，按条目范围与分片参数运行（如 `--items 1-83 --baseline <ref> --candidate <ref>`） |

**交付**：共享库放在 `packages/desktop/scripts/acceptance/`（启动、正常退出、等待、清理、报告）；现有 e-windows 条目迁移为数据驱动的条目表；工作流从 11 个合并为 1 个可复用工作流；**迁移完成并通过 G8.5-3 全量运行前，不删除旧脚本**，最后一个 PR 再统一删除。启动/退出/清理逻辑全仓只允许一份实现（`grep` 唯一）。

**负向自测（必须）**：脚本必须能抓住真问题。在 CI 中注入两个故障，要求验收必须失败：①某设置保存后不落盘；②应用被强杀而非正常退出（必须被标记为违反 H1）。

### 3.5 发版流程（lead 牵头，E 补记录）

**小版本（x.y.Z）准入规则**，写入 `AGENTS.md` 与 lead 手册：
1. 小版本只允许三类内容：R/D/B 类缺陷修复、冻结清单内的可测量样式违例、依赖或版本号。**行为改动必须有计划文档**。
2. 任何发版（含小版本）必须有：计划文档或补丁说明（`docs/plan/YYYY-MM-DD-vXYZ-patch.md`：范围、PR 清单、验收结果）、看板 issue、Windows/macOS CI、`ui:check` 输出、手册 §7 发布清单。
3. 同一工作日最多发布 1 个版本；B 类阻断除外。非阻断样式问题攒到下一个有计划的版本。
4. 规则适用于所有执行者，包括用户直接发起的 codex 会话。

## 7. 对 playbook 的补充

1. 验收脚本问题先归类为 `harness_error` 或 `assertion_failed`，再决定是否改产品代码；`harness_error` 不得推动产品代码修改。

4. 任何需要调整本文 Gate、阈值或不变量的事项，直接汇报用户，lead 不自行决定。
5. 沿用手册 §1 的通知事件。
